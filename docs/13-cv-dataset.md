# 13. CCTV 침수 감지

> 작성 2026-08-18 · AI Hub 135 '부산시 침수위험 복합 데이터' 활용 기록

---

## 1. 왜 이 데이터가 필요했나

②CV 모듈은 처음부터 **날씨에 발목이 잡혀 있었다.**

```
8월 중순 시작 → 장마 종료 → 침수 영상 확보 불가
실제로 2026-08-18 거제 호우주의보 때 시도했으나
  03:51 발효 → 08:13 해제 → 18:49 캡처 = 노면이 이미 말라 있었다
```

사람이 재난문자를 보고 움직이는 방식으로는 침수 영상을 얻을 수 없다.
그래서 두 갈래로 접근한다.

| 경로 | 역할 |
|---|---|
| **AI Hub 135 데이터셋** | 이미 라벨링된 침수 영상으로 학습 |
| `scripts/rain_watch.py` | 호우 자동 감시로 실시간 영상 축적 |

```

├ Training    33.8GB
├ Validation   4.3GB  ← 먼저 사용
└ 라벨 포맷: COCO (1280x720)

카테고리 6종
  1 driveway    2 pole   3 pier
  4 water_side  5 water_area  6 rain_gutter

메타데이터
  10분/1시간/3시간 강우량 · 강우관측소 좌표 · 촬영 시각
```

### 핵심 — 같은 카메라의 평상시/호우 짝

```
2023-08-24 00:00  강우 약함    하천 바닥의 징검다리가 보임
2023-08-24 05:00  강우 53mm/h  징검다리 수몰, 산책로·둔치 침수
```

같은 고정 카메라의 5시간 차이 영상이다.
카메라마다 화각·조명·주변 구조가 달라 **다른 지점의 맑은 사진은 대조군이 되지 못한다.**
이 데이터는 그 조건을 만족한다.

## 3. 한계 — 지하차도 침수는 라벨이 없다

```
1_정보지하차도 인근      {driveway: 60,  rain_gutter: 60}
78_동구_초량_제1지하차도  {rain_gutter: 1219, driveway: 60}
```

지하차도 카메라에는 **`water_area` 라벨이 아예 없다.** 차도와 배수구만 표시돼 있어
침수 정도를 판단할 수 없다.

> **이 데이터셋은 하천 수위 감시용이다.**
> 우리가 원했던 "지하차도가 잠겼는가"는 커버하지 않는다.

역할 분담이 필요하다.

| | 담당 |
|---|---|
| AI Hub 135 | 하천 수위 → 범람 위험 (모델 A와 결합) |
| 자체 CCTV 수집 | 도로·지하차도 침수 → 통행 가능 여부 |

## 4. 수위 등급 정의

절대 수심을 알 수 없으므로 **그 카메라의 평상시 수역면적 대비 배율**로 등급을 매긴다.

```
0 평상   < 1.3배
1 증가   1.3 ~ 2배
2 경계   2 ~ 3배
3 위험   3배 이상
```

### 정규화에서 겪은 실패

처음에는 '하위 20% 면적'을 평상시 기준으로 삼았다가 결과가 무너졌다.

```
60_남구_동아건업_앞_고1   기준면적 1px
강우 30~100mm            평균 352.38배      ← 폭발
등급 분포                경계 0.9% < 위험 5.2%  ← 역전
강우 0~1mm               평균 0.42배        ← 1.0 근처여야 정상
```

`water_area`가 0인 프레임이 많은 카메라에서 기준이 0으로 수렴한 탓이다.

**수정**: 0을 제외한 중앙값을 기준으로 쓰고, 기준이 화면의 1% 미만인 카메라는 제외.
→ 카메라 13개 · 3,292프레임이 남았고 분포가 단조 정상화됐다.

```
평상 86.4% · 증가 2.4% · 경계 9.7% · 위험 1.6%
```

## 5. 강우량과 수위의 관계 — 3시간 누적이 우월하다

```
1시간 강우량 기준                3시간 누적 기준
   0~1mm   0.90배  5.7%         0~1mm    0.72배   0.0%
   1~5mm   1.08배 11.5%         1~10mm   0.97배   6.5%
   5~15mm  1.35배 21.8%        10~30mm   1.27배  19.9%
  15~30mm  1.38배 18.1%        30~60mm   1.71배  33.5%  ← 최고
 30~100mm  1.02배 12.4%        60~200mm  1.06배  14.0%
                                (배율 · 경계이상 비율)
```

**수위 예측 모델(GBDT)의 피처 중요도 1위가 `rain_c3`(3시간 누적)였는데,
영상 데이터에서도 같은 결론이 나왔다.** 강우와 수위 사이에는 시차가 있어
"지금 내리는 비"보다 "그동안 쌓인 비"가 현재 수위를 더 잘 설명한다.

60mm 이상에서 꺾이는 것은 표본이 114건뿐이라 단정하기 어렵다.

## 6. 학습 데이터 분할 — 클립 단위

```
전체 3,292프레임 · 401클립 · 카메라 13개

train  302클립 · 2,519프레임   경계이상 278
val     99클립 ·   773프레임   경계이상  93
```

**프레임 단위 랜덤 분할은 금지한다.**
한 클립(같은 1시간 녹화분)의 프레임은 거의 동일한 장면이라,
섞으면 train 장면이 val에 새어 들어가 성능이 가짜로 높아진다.
수위 예측에서 시간축을 지켰던 것과 같은 이유다.

경계이상이 11%뿐이라 **등급별 층화 분할**로 양쪽에 배분했다.

## 7. 모델 구조 — 특징 추출 + 분류기

GPU가 없다(AMD 내장). ResNet18을 3천 장에 fine-tune 하면 CPU로 수십 분이 걸리고
하이퍼파라미터를 바꿀 때마다 반복해야 한다.

```
ImageNet 사전학습 ResNet18 → 512차원 특징 (1회만 추출)
        ↓
LightGBM 분류기 (초 단위 학습 → 실험 반복 가능)
```

표본이 2,519장뿐이라 백본 전체를 미세조정할 만큼 데이터가 많지도 않다.

### 평가 기준

**정확도를 쓰면 안 된다.** 등급 0이 86%라 "항상 평상"이라고 답해도 86%가 나온다.
수위 예측에서 겪은 함정과 같다.

→ **경계이상(2·3등급) 재현율**을 기준으로 본다. 놓치면 사람이 위험해진다.

### 비교 설계

강우량은 이미 확보한 데이터라 함께 넣을 수 있다. 다만 **영상이 실제로 기여하는지**
확인해야 하므로 셋을 나란히 비교한다.

```
① 강우량만 (2피처)
② 영상만 (ResNet18 512차원)
③ 영상 + 강우량
[기준] 항상 '평상'
```

## 9. 학습 결과 — 세 번의 함정을 지나서

### 9.1 궤적

```
①  Validation만(카메라 13개) · 클립 분할     F2 0.884
②  Validation만 · 카메라 분할                F2 0.000
③  전체(카메라 14개) · 카메라 분할 · 4단계    F2 0.775
④  전체 · 카메라 분할 · 이진 · AUC 평가       ROC-AUC 0.872
```

### 9.2 함정 1 — 카메라 배경 암기 (①→②)

클립 단위로 나눴더니 val 카메라 11개가 **전부 train에도 있었다.**
같은 배경을 이미 본 상태라 F2 0.884는 낙관적으로 편향된 값이었다.

카메라 단위로 다시 나누자 결과가 이렇게 됐다.

```
경계이상 113건을 전부 '평상'으로 예측 — "항상 평상"과 동일한 성능
```

모델이 학습한 것은 물의 모습이 아니라 **"이 카메라의 이 배경 = 등급 2"** 였다.

> 수위 예측에서 관측소 단위로 나눴던 것과 같은 검증이 CV에도 필요하다.

### 9.3 함정 2 — 표본 부족 (②→③)

Training 라벨을 합쳐 경계이상 표본을 **371 → 3,358건(9배)** 으로 늘렸다.
(zip에서 특징을 추출한 4,823프레임 기준으로는 3,310건. 파일명이 겹치는 프레임 일부가 빠졌다.)
카메라 수는 13 → 14개로 거의 그대로였는데도 F2가 0.000 → 0.775로 회복됐다.
**표본이 늘자 배경 암기 전략이 통하지 않게 된 것이다.**

전체 카메라 30개 중 14개만 쓸 수 있었다. 나머지 16개(기아오토큐·하나로한의원 등)는
도로 감시 카메라라 `water_area` 라벨이 없다.

### 9.4 함정 3 — 왜곡된 클래스 비율에서의 F2 (③→④)

4단계로는 등급 3(위험)의 98%를 놓쳤다(170건 중 3건만 정답).
표본이 감당하지 못하는 세분화였다. 대피 판단에 필요한 것은
"얼마나 위험한가"가 아니라 "위험한가"이므로 **평상(0,1) vs 경계이상(2,3)** 으로 합쳤다.

그러자 이런 결과가 나왔다.

```
③ 영상+강우량    F2 0.790
[기준] 항상 경보  F2 0.891   ← 아무 판단 없이 전부 경보만 해도 1등
```

**샘플링이 val 양성 비율을 62%로 부풀린 탓이다**(실제 분포는 10.1%).
이 비율에서는 F2가 재현율에 가중을 주므로 "항상 경보"가 유리해진다.

> **아무 판단도 하지 않는 전략이 최고 점수를 받는 지표는 쓸 수 없다.**

→ 클래스 비율에 흔들리지 않는 **ROC-AUC**로 교체했다. '항상 경보'는 정의상 0.5다.

## 10. 최종 성능

```
                ROC-AUC   PR-AUC
① 강우량만        0.672    0.753   약함
② 영상만          0.818    0.903   쓸만함
③ 영상+강우량     0.872    0.921   우수
[항상 경보]       0.500    0.621   판별력 없음

피처 기여도: 영상 95.0% · 강우량 5.0%
```

**학습에 없던 카메라 5대에서 측정한 값이다.** 영상이 강우량만으로는 알 수 없는 정보를 준다.

해석할 때 주의할 점:
- 5대 중 2대(연안교 하류, 세병교 하류)는 같은 다리의 반대 방향 카메라가 학습에 있다.
- 양성 프레임이 있는 카메라는 3대이며, 검증 양성 991건 중 821건(83%)이 온천교 1대에서 나온다.
- 같은 호우 사건(08-24, 09-01, 09-16)이 학습과 검증에 모두 들어 있다.
- 검증셋을 조기 종료에도 썼다. 조기 종료 없이 600라운드로 고정하면 영상+강우량 0.886,
  영상만 0.844, 강우량만 0.622로, 영상 기반 결과는 유지되고 강우량 단독 결과는 낮아진다.

### 운영 문턱 — 실제 분포로 환산

val 양성 비율(62%)이 실제(10.1%)와 다르므로, 운영 시 헛경보를 환산해 제시한다.

```
문턱   재현율   실제분포 정밀도   1000프레임당 헛경보
0.70   63.6%      57.5%             47건
0.50   77.2%      31.6%            169건
0.35   89.5%      19.0%            386건   ← 권장
0.25   96.2%      13.4%            626건
```

**문턱 0.35 권장.** 열 중 아홉을 잡는다. CCTV는 연속 감시이므로
**몇 프레임 연속 경보일 때만 알리면** 헛경보가 크게 줄어든다.

## 11. 남은 과제

- **차분 영상** — 같은 카메라의 평상시 프레임과의 차이를 입력으로. 배경을 원천 상쇄한다

- Training 원천 33.8GB는 풀지 않았다. zip에서 직접 읽어 필요한 4,823장만 사용
